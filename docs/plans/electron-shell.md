# Electron shell (plan)

Status: **Accepted (stage 1)** — scope settled 2026-10-06 by owner answers
(remote-URL wrapper, Windows installer first, bare window). Stage 1 is
implemented in `apps/desktop`; every follow-up below needs its own go-ahead.

## Context (researched from the repo, then decided)

- `apps/web` is a full Next.js App Router shell: SSR pages plus API routes.
  The tRPC client uses same-origin `/api/trpc` in the browser. A desktop
  shell must not bundle the Next server; it renders the deployed backend over
  HTTPS (same constraint as `apps/mobile`).
- Backend is live: `https://noted-six-chi.vercel.app` (see
  `docs/deployment.md`), so no sequencing wait like the paused Capacitor
  grill.
- Realtime is SSE with the Firebase ID token in connection params;
  queries/mutations use the `Authorization` header. A remote-URL window
  reuses both untouched.
- Auth is Firebase Google behind the server seam. Popups work in an Electron
  `BrowserWindow` (unlike the mobile webview, which uses the redirect flow),
  so desktop keeps `signInWithPopup` and needs no web change:
  `isNativeShell()` is false in Electron (no Capacitor bridge).
- Architect rule: `apps/*` are thin shells owning SDKs, auth adapters, env
  wiring, and navigation only; tRPC routers are the only API definition.
- PLAN.md still lists native shells as demo non-goals, but the mobile shell
  shipped anyway (`df0b27e`); desktop follows the same owner waiver.
- Nearest pattern: `apps/mobile` (baked production URL, committed native
  shell, separate packaging script outside the turbo `build` task).

## Scope contract

- **This stage delivers:** the `apps/desktop` thin shell, this plan, and the
  architect skill update. Implementation ran in the same stage per the
  owner's "lets now work on electron port" plus the settled scope answers.
- **Done means:** gates green; dev launch against localhost works; an
  unsigned Windows NSIS installer builds and its packaged app boots
  production.
- **Follow-up stages** (icon, signing, auto-update, macOS/Linux, preload
  natives) each need their own go-ahead.

## Goals / non-goals

Goals: a bare desktop window on the production URL; a Windows installer
artifact; zero API duplication; popup auth working as-is.

Non-goals (stage 1): bundled or offline UI; custom icon; code signing;
auto-update; macOS/Linux builds; preload native APIs; file
dialogs/notifications/tray.

## Decisions (settled 2026-10-06)

- **Shell strategy:** remote-URL wrapper mirroring mobile.
  `BrowserWindow.loadURL()` reads `src/start-url.ts`: packaged builds load
  the baked `PRODUCTION_URL` literal; unpackaged runs take `APP_URL` when
  set, else `http://localhost:${PORT ?? 3000}`. Both vars were already in
  `turbo.json` globalEnv, so the pipeline is untouched.
- **Platforms/distribution:** Windows NSIS installer first via
  electron-builder (`oneClick: false`), unsigned, brand icon embedded from
  `resources/icon.ico` (multi-resolution, generated by the `assets` task
  from the committed brand-master artwork).
- **Native scope:** bare window. No preload script, locked-down
  `webPreferences` defaults (context isolation on, Node integration off),
  standard lifecycle handlers only.
- **Auth:** desktop keeps the popup; no web change.
- **Packaging:** zero runtime dependencies (plain `process.env`, no dotenv;
  nearest precedent `apps/mobile` reads no env at all). `tsc` emits `dist/`;
  the packager ships `dist/**` plus `package.json` minus test output.
  `version: 0.0.0` exists only because electron-builder requires it
  (siblings carry no version).
- **Boundaries:** no Next boundary markers on the Electron main process
  (plain Node outside the server/client model; mirrors mobile setting no
  boundary config). Desktop imports nothing internal, so the dependency
  direction holds.
- **Shared-config touch:** vitest `include` widened to `apps/*/src` (was
  `apps/web/src` only); `electron` added to `onlyBuiltDependencies` (its
  postinstall fetches the binary); `apps/desktop/release/` gitignored.
- **Turbo:** desktop joins `dev`/`build`/`lint`/`typecheck`/`format`.
  `build` is `tsc` only; `build:installer` stays a separate script so CI
  never signs or packages (same split as mobile's `build:apk`).

## Constraints

- Windows-first dev machine; installer unsigned.
- Production URL baked as a literal (mirrors mobile); no staging switch in
  the packaged app.
